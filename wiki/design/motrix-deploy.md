# Motrix Deploy 框架设计

## 摘要

`motrix_deploy` 在训练产物与执行设备之间建立独立的部署边界。训练侧导出自包含策略和版本化任务契约；
部署侧使用同一份 artifact、任务语义和控制会话驱动仿真或真机，不依赖训练框架运行策略。

本文描述当前架构的职责、数据流、生命周期和安全不变量，不作为 API、配置字段或操作步骤的参考手册。
具体使用见[部署教程](../../docs/source/zh_CN/user_guide/tutorial/advanced/motrix_deploy.md)；
导出与输入分层分别见 [ONNX 导出设计](./onnx-export.md)和[命令输入设计](./deploy-command-input.md)。

## 1. 目标与边界

部署需要独立于训练环境重现策略行为，并在连接设备前尽可能发现契约不匹配。
`mxlab play` 用于训练框架内评估，`mxlab deploy` 用于验证可移植产物和设备控制链路，两者职责不同。

核心目标：

- 仿真与真机复用 observation、action 和任务阶段语义，不分别维护推理闭环。
- artifact 明确记录模型、机器人和任务契约，运行时不猜测 tensor、关节或坐标语义。
- 设备差异限制在后端；任务差异限制在版本化 task；训练框架差异限制在导出侧。
- 本地预检先于硬件动作，运行故障产生明确原因并进入停止路径。

非目标：

- 不在部署核心复刻 reward、curriculum、domain randomization 或 checkpoint 加载逻辑。
- 不把所有机器人、传感器和多模态策略抽象为通用计算图。
- 不承诺硬实时、无缝站立控制器切换或经过认证的机械安全。
- 不将离线测试成功等同于真机验证完成。

## 2. 组件职责与依赖

| 组件 | 拥有的职责 | 不承担的职责 |
|---|---|---|
| 训练侧导出集成 | checkpoint 转换、数值一致性验证、训练语义编译 | 设备连接与运行控制 |
| Artifact | 策略载荷、来源和版本化运行契约 | 现场网络、仿真世界和输入设备 |
| Deploy 应用 | 配置加载、预检、组件装配和结果输出 | 设备协议、任务轨迹 |
| Runtime | 执行宿主、调度、仿真推进或硬件运行生命周期 | 解释 policy tensor、决定任务阶段 |
| ControlSession | 读取状态、采集输入、执行 controller、提交命令、故障收尾 | 理解站起、播放、趴下等阶段 |
| Task / Controller | 任务阶段、正常退出、策略接管和任务完成条件 | 通信、睡眠或物理推进 |
| Policy / PolicyProcessor | 模型推理，以及训练一致的 observation/action 转换 | 持有设备控制权 |
| Robot 后端 | 状态与命令转换、设备控制权、能力和硬件安全边界 | 推导策略输入、执行正常任务轨迹 |

依赖保持单向：

- `motrix_deploy` 依赖 backend-neutral core，不导入具体训练框架、仿真器或硬件 SDK。
- `motrix_deploy_tasks` 实现具体任务；仿真与 Unitree 插件实现具体后端。
- `motrix_robots` 提供可复用模型与关键姿态，不依赖部署硬件插件。
- 训练侧集成可以依赖部署契约生成 artifact；部署不反向加载训练环境。

公开边界通过数据契约和插件发现连接，不以文件布局、内部辅助函数或构造参数作为架构约束。

## 3. 端到端数据流

产物生成分为三个独立步骤：

1. **策略导出**：训练框架 adapter 将 checkpoint 转为自包含 ONNX，并验证数值一致性。
2. **任务编译**：部署 profile 从训练快照和模型提取机器人、任务与控制契约，并与策略 tensor 契约交叉校验。
3. **产物写入**：校验完整 manifest、载荷和校验和，生成可独立读取的 artifact。

运行时则按以下方向传递数据：

> 机器人状态 + 高层任务命令 → task/controller → observation → policy → action 转换 → robot command → 后端。

准备动作和正常退出轨迹是确定性控制行为，不需要伪造 observation 或 policy action。
同一个任务在不同后端上必须复用版本化的策略转换语义。

## 4. 公共契约与不变量

### 4.1 机器人与关节语义

`RobotSpec` 是 artifact 内自包含的机器人契约，不持有 simulator model 或 SDK handle。
关节名称是唯一的规范顺序：状态、目标、增益、缩放和限位按同一顺序排列，后端按名称建立映射。
缺失、重复或不兼容的关节在启动前拒绝，不能靠数组位置或填零掩盖差异。

单位采用 SI；四元数顺序、姿态方向和速度表达坐标系必须显式约定。
当前公共姿态使用 `xyzw`、body-to-world 旋转，角速度在 body frame 表达。
后端不能将不可获得的真机量伪造成仿真 ground truth。

### 4.2 状态新鲜度

`RobotState` 表达当前最新一致快照。读取可以返回同一采样，但不能刷新其原始接收时间。
硬件打开时有界等待首帧有效状态，持续读取不以“必须等下一帧”驱动控制周期。

状态新鲜度依据本机单调时钟检查，设备采样时间用于表达采样顺序。
状态过期、时间倒退或无效状态必须使执行失败，不能通过重新打时间戳掩盖。

### 4.3 命令与所有权

公共命令支持关节伺服和直接力矩两种形式。策略转换先执行任务限幅，后端再执行设备边界检查；
最终有效范围不能宽于 artifact 和硬件限制的交集。
异步后端取得提交命令的独立所有权，调用者之后的数组修改不能改变已校验目标。

命令输入与电机命令是两个不同层次：输入设备产生事件，binding 将事件转换为高层任务命令，
controller 再结合状态生成电机命令。自主 controller 可以没有外部输入；需要输入的任务不能静默补零。

### 4.4 策略与任务版本

Policy 只负责 observation 到 action 的映射；训练 normalizer 和确定性输出头必须包含在导出模型中。
Task 拥有 observation 顺序、历史、动作处理和任务阶段。
模型结构版本与任务语义版本独立管理，语义不兼容的变化不能悄悄复用旧 task 标识。

## 5. 生命周期与控制权

一次部署依次完成：

1. 加载 artifact 和 policy，验证本地配置，组装 task、robot 和 session。
2. Runtime 验证会话和调度条件，调用 `robot.acquire_control()` 获取设备控制权。
3. Session 打开设备、读取有效状态、初始化 controller，并按设备要求启用输出。
4. Runtime 驱动控制循环，task 自己决定准备、策略接管与正常退出。
5. 停止输出并释放设备、线程及宿主资源。

控制权获取是显式设备生命周期操作，不藏在构造器或 `open()` 中；无需交接的后端默认无操作。
Runtime 负责调用时机，robot 负责设备过程，不派生型号专属 runtime。

### Go2 的交接边界

若官方模式仍活动，Go2 要求人工授权 StandDown，随后人工确认动作结束且机体有稳定支撑，才释放官方模式。
交接完成并复查后才启动低层控制。已释放时跳过官方动作。

取消不能回滚已发生的运动；释放后退出也不会自动恢复官方控制。
官方 StandDown 用于交出控制权，task 的站立准备用于满足策略初始条件，二者不可混为同一阶段。
G1 保持其独立的型号启动流程，不能套用 Go2 交接过程。

## 6. 控制执行与正常退出

Runtime 拥有调度和宿主，ControlSession 执行状态—输入—controller—命令闭环。
Controller 不持有 scheduler，不睡眠，也不推进物理。
仿真可以固定步长执行；真机使用实时调度。控制时间和墙钟耗时分别计量。

控制周期与设备传输周期不是同一个概念。Go2 后端采用周期发布和单个最新命令槽，
新命令覆盖未发出的旧命令，避免积压和追赶式突发。该机制不构成硬实时保证。

正常任务阶段属于 task：

- Go2 由操作员启动站立准备，实测就绪后再次确认策略接管。
- Go2 的正常结束请求在准备启动后执行内置、受有效关节范围约束的趴下过渡，再阻尼结束；尚未开始准备时只阻尼结束。
  受限目标可能只形成浅趴，不能保证机体贴地。退出目标不作为用户配置暴露。
- G1 的准备、策略驻留和 motion 播放由对应任务编排，不由通用 runtime 解释。

准备和退出命令不消耗 policy 推理预算。任务正常完成与取消、故障退出必须在结果中区分。
具体按键和操作步骤只在用户教程维护，不在设计文档展开参数参考。

## 7. 故障与资源安全

必须保持以下不变量：

- 本地可发现的契约错误先于设备动作；首帧和实际能力等在线条件仍需在连接后验证。
- 非有限数值、状态过期、无效输入、设备错误和急停进入故障停止，不继续策略输出。
- 正常趴下轨迹不用于失联、超时或急停；这些情况下不具备执行轨迹的可靠前提。
- Go2 的通信 watchdog 故障锁存，新命令不能静默恢复故障会话。
- 先撤销主动输出并尝试设备声明的停止行为，再释放通信；停止和关闭应幂等。
- 若底层写入阻塞，关闭必须明确失败，不能释放仍被工作线程使用的资源。

软件急停、阻尼和命令限位不保证机械支撑，也不限制所有情况下的 PD 总输出力矩。
网络异常时停止命令本身可能无法送达。真机测试必须配置独立急停、承重保护和现场操作人员。

## 8. Artifact 与配置所有权

### 8.1 Artifact 边界

Artifact 包含 manifest、策略及任务所需载荷。载荷通过 artifact 内的相对路径引用，并记录校验和。
运行时不能根据文件名、checkpoint 后缀或训练环境默认值补全缺失契约。
仿真世界和现场设备连接不属于 artifact，但必须与 artifact 中的机器人和控制要求兼容。

### 8.2 Manifest 内容

| 内容 | 权威范围 |
|---|---|
| 载荷与来源 | 模型格式、文件完整性、可追踪的训练来源 |
| Policy 契约 | 输入输出名称、类型与形状 |
| RobotSpec | 规范关节顺序、默认参考和运行限制 |
| 版本化 task 与配置 | observation/action 语义所需的训练参数与任务载荷 |
| Control 契约 | 控制周期、状态新鲜度和坐标约定 |

当前 manifest 支持单实例、单输入输出策略和关节控制契约，不宣称支持任意多模态或多资源组合。
任务配置由版本化 task 插件解释并在读取边界验证；未知任务、重复插件和不兼容版本必须明确报错。
单独的 ONNX 文件不等于完整 deployment artifact。

### 8.3 部署配置边界

| 配置 | 所属责任 |
|---|---|
| artifact 路径、运行预算、后端选择 | 部署应用 |
| 仿真世界、机器人放置、物理和 viewer | 仿真宿主 |
| 网卡、DDS domain、连接与传输安全参数 | 硬件后端 |
| 准备动作及操作员任务行为 | Task 执行配置 |
| 策略增益、归一化和动作缩放 | Artifact 中的策略／任务契约 |

Task 执行配置在部署入口传递，由 task 校验，不使核心配置了解具体任务字段。
准备动作的增益不覆盖策略增益，现场配置不能扩大设备硬限制。
固定型号的电机映射、协议和硬件限制归后端定义，不暴露为任意接线配置。

## 9. 后端与扩展边界

MuJoCo 与 MotrixSim 插件消费完整仿真场景，不实例化训练环境。
Runtime 持有世界与物理推进，robot 端口只提供状态和命令。
仿真中关节伺服必须使用当前物理状态计算输出并执行限幅，不能仅在策略周期计算一次后忽略子步反馈。
传感器绑定需验证真实语义、坐标和维度，不能用同形状数据代替缺失传感器。

扩展采用已有插件边界：

- 训练框架 adapter 导出新模型来源，不改变部署控制循环。
- Profile compiler 连接训练语义与 artifact，不解析 framework checkpoint。
- Task 插件解释版本化任务并创建 controller。
- Backend 插件提供仿真宿主或硬件接口；部署世界与机器人模型分别选择和组装。

只为实际存在的选择需求保留发现机制，不为 observation term、阶段或输入绑定建立额外 registry。
多输入输出、资源组和通用命名 pipeline 属于后续设计议题，需要具体任务驱动的独立提案；不作为当前能力或预先承诺的兼容路线。

## 10. 验证边界

验证按成本和责任分层：

- 单元与契约测试保护关节映射、数值和时间语义、输入校验、任务转换、异步命令所有权及故障停止。
- 仿真集成验证真实模型与传感器、物理推进、任务和导出策略的一致性。
- 导出验收验证载荷完整性、tensor 契约及训练／部署数值一致性。
- 真机验收验证 SDK 字段、输出频率、机械轨迹、交接与停止行为；必须在受保护现场单独执行。

测试观察公共行为和不变量，不固定内部调用结构或任务调参数值。
结果区分 policy 完成步数、墙钟耗时、调度超限和失败原因；仿真指标由仿真 runtime 单独提供，不能据此推导真机稳定性。
