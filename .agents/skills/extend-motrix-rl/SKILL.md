# Extend Motrix RL

核心原则：**算法只认识数据与契约，不认识具体任务；任务问题在环境或配置层解决，通用运行机制在框架层解决。**

先读适用的 `AGENTS.md` 和当前公共接口；编写 Python 时同时遵循 `motrixlab-code-style`。现有算法只是参考，不把某个实现的结构或超参数当成通用标准。

## 1. 算法与任务解耦

- 算法核心依赖通用 observation、action、reward、termination/truncation 等数据，不依赖具体环境类、机器人、关节、reward term 或任务名称。
- trainer 可通过 registry 和环境标识创建环境，但不得按环境名分支决定算法行为。支持范围按接口能力表达，例如连续动作或可用的观测组，而不是任务白名单。
- 环境缺少算法所需能力时，在契约边界明确报错；需要补齐环境契约时，在环境所有者处实现，不把任务补丁塞进算法。
- 任务配方、专用评估和训练对照可以认识具体任务，但必须位于算法核心之外。

## 2. 配置与实现分离

- 算法配置描述算法能力和超参数；任务配置选择环境并覆写实际差异。网络输入维度等从通用环境描述派生，不硬编码某个任务的尺寸、预算或奖励设置。
- 保持实现、配置和公开注册的所有权清楚。Motrix 自有算法遵循 builtin 的统一注册边界；不要为单个算法另造 framework、发现机制或平行配置体系。
- 不为不同算法强行统一内部结构，也不把某个任务调参结果包装成框架契约。

## 3. 明确状态与所有权

- 模型、normalizer、target、buffer、随机状态和 checkpoint 各有明确的创建、更新、持久化和清理责任。
- 按环境生命周期消费借用输出，明确何时需要自有副本；状态、动作和奖励必须对应同一条 transition。
- 终止、截断、重置及 bootstrap 语义依据公共契约，不依赖特定任务的偶然行为。
- 异步执行明确发布、读取和复用边界；设备优化不能改变算法状态更新语义或掩盖所有权。

## 4. 复用框架机制

- 进程初始化、线程预算应用、设备与 placement、日志及训练产物优先复用框架能力，不在算法中重复实现。
- 异步 RL 方法尽量复用 `motrix_rl` 的基础 transport 工具，包括 transition ring、权重/normalizer 快照和既有 host/CUDA-IPC 协议；算法声明数据 schema 与更新策略，不自行复制 IPC、版本管理或背压机制。确有能力缺口时，在框架工具层补齐并验证，不另建算法私有的平行协议。
- 通用机制归框架，算法特有策略归算法：例如框架应用启动设置，trainer 决定线程预算和 seed 派生；不要让框架猜测算法对象的字段。
- 明确不支持的能力并报错，不静默忽略用户配置，不为具体任务增加隐式兜底。

## 5. 保持最小实现

- 只实现当前需求，不预建多设备、多进程、兼容路径或通用抽象。按实际职责组织代码，不强制复制参考算法的文件布局。
- 实验结束后清理临时 helper、无用状态、过渡配置和仅为 A/B 拆分的中间组合；仍承担 CPU 支持或真实排障职责的路径不视为残留。
- 同一 PR 内直接迁移内部调用方，不为中间版本保留 alias 或兼容层；已发布契约的兼容需求需另行确认。

## 6. 按契约验证

- 通用测试保护算法数学、输入输出、状态转换和数据生命周期；具体环境训练用于效果验收，不反向引入任务专用算法分支。
- loss 有限、权重变化或短跑通过，不等于算法正确或训练效果达标。静态检查、运行时、硬件和训练效果证据分别报告。
- 性能优化先测量定位瓶颈，优先通过 `torch.compile` 与 CUDA Graph 加速可编译的张量计算和稳定的训练执行路径，减少 Python/设备同步与 kernel 启动开销；不以改变算法语义换取速度，也不在没有测量依据时先写自定义 kernel。
- 编译和图捕获须保持状态更新、随机性、buffer 生命周期与 checkpoint 恢复契约。分别验证正确性、启动成本、稳态性能和端到端结果；局部 kernel 或 learner 提速不能代替整体收益。保留负面结果与未验证边界。

## 完成前自查

- 算法是否能在满足同一契约的另一环境上使用，而无需修改算法代码？
- 是否有具体任务知识、通用运行机制或实验残留落在了错误的层？
- 配置、状态所有权与支持范围是否显式，验证证据是否对应所声称的能力？
